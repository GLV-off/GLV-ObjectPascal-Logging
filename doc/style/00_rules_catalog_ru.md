# Каталог правил стиля GLV Log — предложения (v0.1)

Статус: **проект, не принято**. Это вход для сессий S2–S4 плана `doc/style_plan_ru.md`.
Формулировки нормативные (что должно быть), «факт» — что есть в коде на 2026-10-28.

## Как читать

| Колонка | Значение |
|---|---|
| ID | `NN-K` = номер модуля стиля + номер правила; модуль `NN` = файл `NN_*_ru.md` |
| Правило | нормативная формулировка; «должен» = требование, а не описание кода |
| Ур. | `HARD` — блокирует новый код и выдаётся в ревью; `SOFT` — предпочтение, не выдаётся за нарушение; `METRIC` — лимит: требует решения, не блокирует |
| Проверка | `sh` — `scripts/style-check.sh`; `rg` — одна команда; `manual` — только человек/ревьюер |
| Факт | результат проверки на текущем дереве: `OK n/n` или `путь:строка` |

Общее правило: **правило без проверки — не правило**. Если способа проверить нет, оно
уходит в `SOFT` или не вводится вовсе (см. «Что не предлагаю»).

### Баланс уровней — это проблема, а не достижение

27 правил `HARD` с проверкой `manual` — это **непроверяемые** правила. Агент не может
убедиться, что он их соблюдает, значит он либо забудет их, либо (хуже) заявит
«соблюдено», не проверив. Предлагаю понизить 11 из них до `SOFT` и оставить
`HARD/manual` только там, где ошибка ломает контракт библиотеки:

| Оставить `HARD/manual` (16) | Понизить до `SOFT` (11) |
|---|---|
| 02-4, 03-1, 03-7, 03-8, 03-9, 04-1, 04-2, 04-3, 04-4, 04-8, 05-3, 06-7, 08-2, 09-1, 09-2, 10-5 | 01-12, 03-2, 03-6, 04-6, 04-7, 05-4, 06-2, 06-5, 06-8, 07-3, 09-3 |

- Остаются `HARD`: ошибка видна ревьюеру сразу при чтении дифа, и она ломает контракт
  библиотеки (владение, `TLog`, V1/V2, зависимости, `Format` + `UnicodeString`).
- Понижаются до `SOFT`: полезно, но не операционно — в первом же прогоне утонут
  в шуме и обесценят остальные HARD.

После понижения баланс: **44 HARD / 30 SOFT / 3 METRIC**, из HARD автоматически
проверяются 28 из 44. `04-6`/`04-7` (`inherited` последним, `try..finally`) можно
вернуть в HARD, когда они станут `rg`-проверяемыми.

Готовность кода к правилам «как есть»:

| Состояние | Правила |

## Что не предлагаю вводить

| Идея | Почему нет |
|---|---|
| Цикломатическая сложность ≤ 10 | нет парсера/инструмента в окружении; грубый счёт `if/case/while` даёт ложные срабатывания → станет «вкусом» |
| ≤ N публичных методов на класс | не замерено; `TLogBuilder` (16 методов) сломает правило в первый день и подорвёт доверие ко всему гайду |
| Запрет `TThread`/`SyncObjs` | они нужны `TAsyncFileLog`; запрет противоречит контракту библиотеки |
| Обязательный `TearDown` в каждом тесте | не нужен тестам без ресурсов; шум |
| Требование «каждый юнит в пакете» как правило стиля | это `pascal-package-sync`, отдельный скилл |

## Приложение: команды, которыми проверялись факты

```bash
# шапки и ключи
for f in lib/src/*.pas; do sed -n '2,7p' "$f" | grep -oE 'Module:|Author:|Description:|History:' | tr '\n' ' '; echo " $f"; done
# include-файл и его позиция
grep -n "{\$I" lib/src/*.pas test/src/*.pas
# ширина строки
awk 'length>100 {print FILENAME":"FNR": "length}' lib/src/*.pas test/src/*.pas
# табы / не-ASCII / CRLF
grep -lP '\t' lib/src/*.pas test/src/*.pas ; grep -nP '[^\x00-\x7F]' lib/src/*.pas ; file lib/src/*.pas test/src/*.pas
# лимиты: SLOC тела и число параметров (awk, учитывает CRLF и отсутствие отступа у методов)
#   определение счёта — в 10-1; реализация — секция METRIC в style-check.sh (S4)
# зависимости / дженерики
grep -hoP '^\s{2}[A-Za-z][A-Za-z0-9_.]*(?=,?\s*$)' lib/src/*.pas | tr -d ' ' | sort -u
# владение
grep -n 'FreeAndNil\|\.Free\b' lib/src/*.pas
```

Ловушка при написании скрипта (проверено на себе): файлы в CRLF, поэтому
`$0` заканчивается на `\r` — шаблоны вида `/;$/'` и `tail -1 | grep '^end\.$'`
дают ложные срабатывания. Первым делом — `sub(/\r$/, "")`, а «последняя строка»
ищется как «последняя непустая».
