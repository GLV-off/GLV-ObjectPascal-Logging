# Шаблон пункта бэклога

Бэклог — не свалка находок, а очередь изменений. Пункт без доказательства,
последствия и критерия приёмки в бэклог не попадает.

## Поля

| Поле | Обязательно | Правило |
|---|---|---|
| `ID` | да | `BL-001`, `BL-002`…; выдаёт `findings-to-backlog.sh`; вручную не переиспользовать |
| `Класс` | да | ровно `BLOCKER`, `BUG`, `RISK`, `SMELL`, `DOC` — как severity в `code-recon` |
| `Пункт` | да | одно предложение: что изменить, а не «улучшить модуль» |
| `Доказательство` | да | `путь:строка`; цитата ≤3 строк — в отчёте/PR, не обязательно в таблице |
| `Последствие` | да | что сломается/потеряется и при каких условиях |
| `Минимальная правка` | да | 1–3 шага в существующей структуре; без новых зависимостей |
| `Тест/критерий` | да | конкретный тест или проверяемая команда; «стало лучше» не criterion |
| `Размер` | да | `S` — до ~30 строк/один тест; `M` — несколько функций; `L` — меняет слой/API |
| `Риск` | да | `API: breaking` / `второй компилятор` / `доки` / `пакет`; пусто = «нет особого» |
| `Зависит` | да | ID других пунктов или `—`; циклы запрещены |
| `Статус` | да | `new`, `in-progress`, `done`, `wontfix` |

## Статусы

```text
new ──► in-progress ──► done
  │           │
  └───────────┴──────► wontfix (только с причиной)
```

- `new` — подтверждено, не начато.
- `in-progress` — есть исполнитель/ветка; укажите дату и что именно делается.
- `done` — **только** если есть тест, который падал до правки и проходит после,
  или явное решение пользователя с датой. Ссылку на тест/коммит — в пункт.
- `wontfix` — только с причиной: «не баг», «вне поддержки», «дороже, чем риск»,
  «ждём внешнюю зависимость». Без причины статус невалиден.
- Закрывать пункт «потому что код изменился» нельзя: нужен тест или решение.

## Приоритет

- `next` — 3–5 пунктов. В `next` не больше **одного** пункта, ломающего
  публичный API (в этом репозитории такие помечаются `Риск: API: breaking`).
- `later` — всё остальное; порядок внутри не важен.
- `inbox` — только строки от `findings-to-backlog.sh`; после разбора пункт
  переносится в `next`/`later` и получает полные поля.
- Сначала `BLOCKER`, затем `BUG`, затем `RISK`; `SMELL`/`DOC` — если дешевле
  и не блокируют. Не открывайте `BLOCKER` без сборки/теста/потери данных.

## Один пункт = одно изменение + один тест

Плохо:

> «Починить async-логгер и заодно BOM, кодировки и тесты».

Хорошо:

> «`Destroy` теряет `FQueue`: слить очередь в файл; тест — 1000 сообщений →
> `Free` → 1000 строк».

Если правка неизбежно затрагивает два контракта, это два пункта с зависимостью,
а не один «большой».

## Шаблон для вставки

```markdown
| BL-000 | BUG | <что изменить> | `<путь>:<строка>` | <последствие> | <1–3 шага> | <тест/команда> | S/M/L | <риск> | BL-000/— | new |
```

В отчёте/PR к пункту добавьте:

```markdown
### BL-000 — <заголовок>
- Доказательство: `<путь>:<строка>` — `<цитата>`
- Последствие: ...
- Минимальная правка: ...
- Тест: `<файл>::<тест>` — что именно проверяет
- Размер/риск/зависимости: ...
- Статус: new
```

## Пример

`BL-002` из `doc/backlog_ru.md`:

- класс `BUG`, доказательство `lib/src/GlvLogFiles.pas:187`;
- последствие: очередь `FQueue` освобождается без записи, сообщения теряются;
- правка: слить остаток очереди в буфер и вызвать запись до `FreeAndNil`;
- тест: 1000 сообщений, сразу `Free`, прочитать 1000 строк;
- размер `M`, риск `API: no`, зависит от `BL-001`.

## Проверка перед добавлением

- [ ] Есть `путь:строка`, и файл/строка действительно существуют.
- [ ] Последствие описано в терминах поведения, а не «плохой код».
- [ ] Правка не требует новой зависимости/слоя/фабрики.
- [ ] Есть тест, который можно запустить в этом репозитории.
- [ ] Пункт не дублирует существующий ID/доказательство.
- [ ] `API: breaking` отмечен, если меняется публичное поведение/сигнатура.
- [ ] `wontfix` имеет причину; `done` имеет тест или решение.
- [ ] Пункт не является «улучшить всё» и не объединяет несколько изменений.
