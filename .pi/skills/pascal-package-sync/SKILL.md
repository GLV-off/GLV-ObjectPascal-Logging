# Пакеты и проекты: инвентаризация и правка

Пакет — это XML со списком `<Files>/<Item>`. IDE у агента нет, `xmllint` в
окружении нет, поэтому «добавить юнит через IDE» превращается в ручную
правку вслепую. Этот скилл сначала показывает фактическое состояние, потом
даёт точечную правку и проверку сборкой.

## Жёсткие правила

1. **Сначала инвентаризация.** Не добавлять юнит, не посмотрев, в каком пакете он уже есть и какие юниты покрыты.
2. **Пакет — это `Files`.** Юнит из `OtherUnitFiles`, но не из `Files`, компилируется неявно и в пакет не входит — не считать его «покрытым».
3. **Автоген не трогать.** `lib/pkg/lz/*.pas`, `lib/pkg/ct/*.pas` — вывод IDE; `pkg-add-unit.sh` отказывается, если файл начинается с `{ This file was automatically created`.
4. **Не «уравнивать» v1 и v2.** Это разные API; симметрия пакетов — отдельное решение, а не побочный эффект.
5. **CRLF, отступы, сортировка.** Без CRLF diff идёт на весь файл; юниты в `Files` — по алфавиту без учёта регистра.
6. **Одна правка — один пакет.** `.lpi`/`.dproj` не менять в той же правке без просьбы.
7. **После правки — сборка.** Без `build.sh` (S1) «XML валиден» ≠ «пакет собирается».
8. **Никаких `xmllint`/`jq`.** Только `grep`/`awk`/`sed` и `diff`.

## Фаза 1 — инвентаризация

```bash
bash .pi/skills/pascal-package-sync/scripts/pkg-inventory.sh
```

Скрипт читает `lib/pkg/**/*.lpk`, `*.ctpkg`, оба тест-проекта и демо
(`backup/` игнорируется). Ничего не пишет, кроме временного каталога.
Код выхода `0` — инвентаризация построена, `2` — нет `lib/src`/пакетов.

Что означает вывод:

| Строка | Смысл |
|---|---|
| `PKG\|путь\|имя\|kind\|ver\|units=N` | пакет и число юнитов в `Files` |
| `UNIT\|пакет\|юнит` | прямая таблица «пакет → юниты» |
| `UNITPKG\|юнит\|пакеты` | обратная таблица «юнит → пакеты» |
| `COVER\|src=N\|covered=M\|uncovered=K\|missing=…` | покрытие `lib/src/*.pas` |
| `ASYM\|v1=…\|v2=…\|both=…\|v1_only=…\|v2_only=…` | асимметрия экосистем |
| `AUTOGEN\|пакет\|ok\|desync\|missing` | сверка автоген-юнита с `Files` |
| `REQ\|проект\|пакеты` | `RequiredPackages` проекта |
| `DUP\|проект\|юнит\|search=…` | юнит из `<Units>` есть и в `OtherUnitFiles` |
| `OVL\|проект\|пакет\|юнит` | юнит пакета попал в путь поиска проекта |
| `REQUIRED\|пакет\|FCL/adFCL/…` | зависимости пакета |
| `SUMMARY\|…` | счётчики для журнала |

Ожидаемое состояние на 2026-10-28: `COVER 13/16` (нет `GlvLogConsole`,
`GlvLogContract`, `GlvLogEngine`), `ASYM v1=8|v2=5`, `DUP` — 8 строк
(по 4 тест-юнита в каждом `.lpi`), `AUTOGEN` — все `ok`, `OVL|none`.

Расхождение с этим снимком — факт для журнала/бэклога, а не повод править
код в этой сессии.

## Фаза 2 — решить, куда добавлять

| Юнит | Пакет | Почему |
|---|---|---|
| `GLV.Log`, `GLV.Log.Lvl`, `GLV.Log.Engine` | `lib/pkg/lz/glv_log_contract.lpk` | контракт v2 |
| `GLV.Log.ConsoleEngine`, `GLV.Log.SyncFileEngine` | `lib/pkg/lz/glv_log_def_engine.lpk` | движки v2 |
| `GlvLog*` (v1) | `lib/pkg/ct/glv_log_def_engine.ctpkg` | единственный v1-пакет |
| новый юнит v1 | `.ctpkg` | v1 собирается только CodeTyphon |
| новый юнит v2 | `.lpk` по слою (contract/engine) | не смешивать слои |
| тест/демо-юнит | `<Units>` соответствующего `.lpi`/`.dproj` | это проект, не пакет |

Если юнит нужен и v1, и v2 — сначала решить, не дубль ли это API; пакеты
не обязаны быть симметричными.

## Фаза 3 — добавление в пакет

Всегда сначала `--check` (пишет только в temp, пакет не меняет):

```bash
bash .pi/skills/pascal-package-sync/scripts/pkg-add-unit.sh \
  lib/pkg/lz/glv_log_contract.lpk lib/src/GLV.Log.NewEngine.pas --check
```

Скрипт:

- берёт имя из `unit …;` и путь относительно каталога пакета (`..\..\src\…`,
  обратные слэши);
- вставляет `<Item>` в алфавитное место внутри `<Files>`, сохраняя CRLF и
  отступы; diff должен содержать только 4 добавленные строки;
- `RESULT|skip|already-present` и код `3`, если `UnitName` уже есть;
- `RESULT|refuse|autogenerated` и код `2`, если пакет или юнит — автоген;
- `WARN|autogen|…` — автоген-юнит рядом не обновлён (это нормально:
  пересоберите/установите пакет в IDE).

Применить (без `--check`):

```bash
bash .pi/skills/pascal-package-sync/scripts/pkg-add-unit.sh \
  lib/pkg/lz/glv_log_contract.lpk lib/src/GLV.Log.NewEngine.pas
```

Ручной fallback — только если скрипт недоступен; вставить в `<Files>`:

```xml
      <Item>
        <Filename Value="..\..\src\GLV.Log.NewEngine.pas"/>
        <UnitName Value="GLV.Log.NewEngine"/>
      </Item>
```

и затем всё равно проверить `pkg-inventory.sh` + сборку.

## Фаза 4 — проверка

```bash
bash .pi/skills/pascal-package-sync/scripts/pkg-inventory.sh | grep -E '^(COVER|AUTOGEN|DUP|SUMMARY)\|'
bash .pi/skills/pascal-build-probe/scripts/build.sh lib-v2   # или lib-v1-ct
git diff --stat && git status --porcelain
```

Ожидается: юнит в `UNITPKG`, `COVER` вырос, `AUTOGEN` — `ok` (или `desync`/`missing`, если IDE не перегенерировала), сборка `RESULT|…|ok`, в `git status` только намеренные файлы и никаких `*.ppu`/`*.o`/`*.exe`.

## 10 проверок (каждая — готовая команда)

1. **Инвентаризация целиком:** `bash .pi/skills/pascal-package-sync/scripts/pkg-inventory.sh` — exit `0`.
2. **Состав пакетов:** `… | grep '^PKG|'` — 3 пакета, `units=8/3/2`.
3. **Покрытие:** `… | grep '^COVER|'` — `13/16`, `missing=GlvLogConsole,GlvLogContract,GlvLogEngine`.
4. **Асимметрия:** `… | grep '^ASYM|'` — `v1=8`, `v2=5`, `both=no`.
5. **Автоген:** `… | grep '^AUTOGEN|'` — три строки `ok` (две с одинаковым именем — различать по пути).
6. **Дубли поиска:** `… | grep '^DUP|'` — 8 строк, `search=..\..\src`.
7. **Зависимости:** `… | grep '^REQUIRED|'` — `adFCL` у `.ctpkg`, `FCL`/`FCL,glv_log_contract` у `.lpk`.
8. **Пробное добавление:** `T=$(mktemp -d); mkdir -p "$T/lib/pkg/lz" "$T/lib/src"; cp lib/pkg/lz/glv_log_contract.lpk "$T/lib/pkg/lz/c.lpk"; cp lib/src/GlvLogConsole.pas "$T/lib/src/"; bash .pi/skills/pascal-package-sync/scripts/pkg-add-unit.sh "$T/lib/pkg/lz/c.lpk" "$T/lib/src/GlvLogConsole.pas" --check` — в diff только `<Item>`.
9. **Отказы:** повторно добавить существующий `GLV.Log` → `RESULT|skip|already-present`, exit `3`; файл с маркером автогена → `RESULT|refuse|autogenerated`, exit `2`.
10. **Сборка после правки:** `bash .pi/skills/pascal-build-probe/scripts/build.sh lib-v2` и `… lib-v1-ct` — `RESULT|…|ok`; иначе — лог в `out/probe/`.

## Известное состояние (вход для S5)

- Вне пакетов: `GlvLogConsole`, `GlvLogContract`, `GlvLogEngine` (прототипы v2) — долг, не ошибка инвентаризации.
- `glv_log_def_engine` есть в двух экосистемах с разными наборами — сравнивать по пути.
- Уточнение к F10: `OtherUnitFiles` тест-проектов указывает на `test/src`
  (а не `lib/src`), поэтому 8 `DUP` — это тест-юниты, описанные и в
  `<Units>`, и в поисковом пути. Отдельно пакеты смотрят в `lib/src` и
  подтягивают не перечисленные в `Files` юниты неявно — это `OVL`/риск
  «скомпилировалось, но не в пакете».

## Не дублировать

- `code-recon` — read-only ревью и находки; здесь инвентаризация уже
  специализирована под пакеты, но дефекты кода не ищутся.
- `design-brainstorm` — варианты дизайна, не XML-правки.
- `pascal-build-probe` (S1) — детект тулчейна и сборка; здесь только
  вызываем его в конце.
- `test-cross` (S3) — написание тестов и харнесс; здесь тест-проекты только
  как потребители пакетов.
- `doc-sync-ru` (S4) — сверка доков с кодом; здесь доки не правим.
- `backlog-from-review` (S5) — найденные расхождения туда, не «чиним» здесь.
