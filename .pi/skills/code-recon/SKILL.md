# Разведка и ревью кода

Всегда две фазы и именно в этом порядке:

1. **Разведка** — что здесь есть, как связано, что считается нормой (правила,
   контракты, точки сборки).
2. **Ревью** — что не так, чем это подтверждается, что с этим делать.

Пропущенная разведка — главная причина ложных находок: «дефект» оказывается
осознанным контрактом, зафиксированным в тестах.

## Жёсткие правила

1. **Ревью read-only.** Ничего не править, не «заодно улучшать», не создавать
   файлов, пока пользователь явно не попросил исправление.
2. **Каждая находка — `путь:строка` + короткая цитата (≤3 строки).** Что не
   прочитал своими глазами — не утверждай. Догадку помечай `[гипотеза]`.
3. **Не выдумывать результаты сборки и тестов.** Нет компилятора/пакетов —
   пиши «не проверено» и чего именно не хватает. Отсутствие проверки — это
   факт отчёта, а не пробел, который можно замазать.
4. **Документация — заявка, а не истина.** AGENTS.md/README/doc описывают
   намерение; расхождение текста и кода — отдельная находка (класс `DOC`),
   а не повод молча подогнать код под текст.
5. **Факты выше вкуса.** Стилевые придирки не ставятся выше блокеров и не
   выдаются за нарушение правил проекта. Если правило проекта не найдено
   в тексте — это мнение, а не нарушение.
6. **Не тащить новое.** Не предлагать зависимости/фреймворки/слои, если задача
   решается в существующей структуре. Находки, ломающие публичный API,
   помечать отдельно: они дороже, чем кажутся.

## Фаза 1 — Разведка

### Шаг 1.1. Снимок репозитория

```bash
bash scripts/recon.sh .        # скрипт этого скилла; аргумент — корень репо
```

Скрипт печатает: ветку/HEAD/грязность, файлы по верхним каталогам с числом
строк, крупнейшие файлы, точки сборки (`.lpi .lpk .dproj .ctpkg .lpr .dpr`,
а также `Makefile package.json *.sln`), найденные файлы правил, рёбра
`unit -> uses` (только interface-часть), маркеры `TODO|FIXME|HACK|XXX|deprecated`
и подозрительные артефакты в трекинге. Если `rg` нет — скрипт откатывается на
`grep`; если нет git — работает по `find`.

Дополни вручную, чего скрипт не знает:

```bash
git status --porcelain          # незакоммиченное = зона риска
git diff --stat                 # что именно менялось
git log --oneline -10           # о чём репозиторий сейчас
```

### Шаг 1.2. Прочитать правила проекта (целиком, не по диагонали)

Ищи и читай: `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `README.md`, `doc/**`,
`.editorconfig`, `.gitattributes`, настройки линтеров/CI. По умолчанию — весь
файл: правила живут в середине («известные дефекты», «контракты, которые нельзя
ломать»), а не в первом абзаце.

Выпиши из них **чек-лист инвариантов** — короткие проверяемые утверждения:

- обязательные конвенции (шапка файла, include-директивы, режимы компилятора,
  стиль имён, переносы строк/кодировка);
- публичные контракты (форматы строк, сигнатуры, уровни, алиасы фасада);
- правила владения ресурсами (кто `Free`, кто владеет детьми);
- мультиплатформенность/мультикомпиляторность (что должно собираться и где);
- процессы (как добавлять новый модуль, где регистрировать тесты, что обновлять в доках);
- объявленные долги: их можно **подтверждать**, но нельзя выдавать за новые находки.

### Шаг 1.3. Зафиксировать карту

Пиши карту до ревью, чтобы не путать слои:

```text
назначение репо (1-2 строки)
точки входа / фасад / публичный API
граф модулей (слои, кто кого видит; циклы и нарушения слоёв — кандидаты в находки)
внутренние (не публичные) модули
тесты (что реально проверяется, где флаки)
сборка (пакеты/проекты, автогенерируемые файлы — их не ревьюим как код)
доки (какие обещания даны пользователю)
незакоммиченное/в работе
```

Детали и типовые красные флаги — в `references/recon-checklist.md`.

## Фаза 2 — Ревью

Иди по осям; на каждой оси либо находка, либо явное «N/A, потому что …».
Не растекайся: ось без находок закрывается одной строкой.

1. **Контракты и API.** Совпадает ли фактическое поведение с заявленным
   форматом/сигнатурой? Проверяй по тестам и по коду-потребителю, не по README.
2. **Инварианты сборки.** Компиляторо-специфичный код, директивы, кодировки и
   переносы строк, условная компиляция, автогенерируемые файлы.
3. **Владение ресурсами.** Кто освобождает, двойное освобождение, утечки,
   `try/finally` вокруг файлов/потоков/потоков-исполнения, отмена владения.
4. **Потоки и асинхронность.** Гонки, отсутствие ожидания/сигналов, `Sleep`
   в тестах, общий буфер без блокировки, потеря данных в очереди при остановке.
5. **Ошибки и молчаливые отказы.** Проглоченные исключения, функции, всегда
   возвращающие одно и то же, «заглушки» вместо логики, обрезанные данные.
6. **IO, кодировки, границы.** Усечение при перезаписи, BOM, нормализация
   путей, частичная запись, обработка пустого/огромного входа.
7. **Тесты.** Покрыто ли изменённое поведение, не флакуют ли (тайминги, ФС),
   не проверяют ли реализацию вместо контракта.
8. **Сборка и пакеты.** Модуль добавлен в проекты/пакеты, автоген не правили
   руками, дубликаты алиасов не разъехались.
9. **Долги и мёртвый код.** `TODO/FIXME`, `deprecated`, `backup/`, заготовки,
   недостижимые ветки, комментарии, противоречащие коду.
10. **Доки.** Таблицы форматов, примеры, карты зависимостей — против реальности.

## Severity (использовать ровно эти метки)

- `BLOCKER` — не собирается / теряются данные / сломан публичный контракт /
  утечка при штатном сценарии.
- `BUG` — воспроизводимо неверное поведение в обычных условиях.
- `RISK` — дефект при определённых условиях (нагрузка, гонка, большой вход,
  другой компилятор). Помечай, при каких.
- `SMELL` — мешает менять код, поведение не ломает.
- `DOC` — код и документация/комментарии расходятся.

## Формат отчёта

Скелет — `references/report-template.md`. Обязательные части:

1. **Что проверено** (оси + что реально читал) и **что не проверено** (сборка,
   тесты, рантайм — с причиной).
2. **Карта** из шага 1.3, кратко.
3. **Находки** — по убыванию severity, с `путь:строка`, цитатой, объяснением
   последствий и минимальной правкой. До 15 находок в основном списке,
   остальное — компактным «прочее».
4. **Расхождения документов с кодом** — отдельным блоком (это дешёвые и самые
   полезные находки).
5. **Рекомендуемый порядок работ** — 3-5 пунктов, с указанием, какие находки
   стоит закрывать одним изменением и с каким тестом.

## Когда просят не только ревью, а исправление

Только после явного запроса. Тогда: одна находка = одно осмысленное изменение
+ тест; формат вывода меняется — сначала правятся ожидания в тестах; новые
модули регистрируются там, где требует проект (пакеты/проекты, а не только
каталог исходников); таблицы и карты в доках обновляются в том же изменении;
`git status` не содержит артефактов сборки; если окружение не даёт собрать или
прогнать тесты — так и написать, не выдумывая «зелёный» результат.
