# Чек-лист разведки и красные флаги

Справочник к `SKILL.md`. Задача — за один проход собрать факты, которых хватает
для честного ревью, и не перепутать «так задумано» с «так сломалось».

## 1. Инвентаризация

- [ ] Границы репозитория: где исходники, где артефакты сборки, что в `.gitignore`.
- [ ] Объём: файлы по верхним каталогам, число строк, 5-10 крупнейших файлов
      (с них начинать чтение логики).
- [ ] Состояние: ветка, HEAD, незакоммиченные изменения, последние коммиты.
      Грязное дерево — всегда отдельная зона риска в отчёте.
- [ ] Что отслеживается, но выглядит как артефакт (`out/`, `*.ppu`, `*.o`,
      `*.exe`, `*.log`, `*.lps`, `*.res` рядом с исходниками) — находка класса `SMELL`.
- [ ] Мусор-заготовки: пустые модули, файлы-заглушки, `backup/`, `.tmp_*`.

## 2. Точки входа и публичный API

- [ ] Найди фасад(ы): единый модуль, через который библиотека/приложение
      используется. Всё, что не в фасаде — внутреннее, его правки дешевле.
- [ ] Перечисли публичные типы/функции фасада и их обещания (форматы, уровни,
      поведение по умолчанию).
- [ ] Проверь примеры из README компиляционной головой: реально ли эти имена
      и `uses` существуют в текущем дереве.

## 3. Граф зависимостей

- [ ] Рёбра «модуль → что использует» по interface-части (`implementation` — не
      архитектурное ребро, а деталь).
- [ ] Слои: есть ли направление (типы → база → реализации → фасад) или циклы.
- [ ] Нарушения слоёв: внутренний модуль в фасаде, реализация в interface,
      «удобный» `uses` ради одного типа.
- [ ] Сверь объявленный граф (доки) с фактическим — расхождение = `DOC`.

## 4. Сборка

- [ ] Точки сборки: `*.lpi *.lpk *.dproj *.ctpkg *.lpr *.dpr`, `Makefile`,
      `package.json`, `*.sln/*.csproj`, CI-конфиги.
- [ ] Автогенерируемые файлы (например `*.lpk`-компаньоны `*.pas` у Lazarus)
      помечай как «не ревьюить», но проверь: новый модуль **добавлен**?
- [ ] Правила/режимы компилятора и include-файлы: соблюдаются ли в каждом юните.
- [ ] Мультиплатформенность: код под `{$IFDEF}` — обе ветки правдоподобны?
- [ ] Наличие компилятора в окружении — зафиксируй для раздела «не проверено».

## 5. Тесты

- [ ] Где тесты, чем запускаются, какие внешние пакеты нужны.
- [ ] Что реально проверяется: контракт или внутренняя реализация.
- [ ] Флаки: `Sleep`, файловая система, время, порядок потоков, локали.
- [ ] Мёртвые/помеченные `deprecated` тесты; пустые заготовки тест-модулей.

## 6. Документация

- [ ] Список доков и что каждый обещает (пользовательский API, внутренняя карта,
      чек-листы, требования).
- [ ] Таблицы форматов/контрактов — сверять построчно с кодом.
- [ ] Язык/кодировка/переносы строк доков относительно остального репо.

## Типовые красные флаги (Pascal / Object Pascal)

- `Position := 0` без `Size := 0` при перезаписи файла → «хвост» старых байт.
- Запись BOM, затем безусловный сброс позиции → BOM затирается.
- Проверка «непустой файл» по не-заполненному буферу → всегда `False`.
- Поток-наследник `TThread.Execute` без `Sleep`/`Event` → холостое вращение.
- Условие `Count >= 0` (всегда истинно) как «есть данные» → работа на каждой
  итерации и/или перезапись.
- `Free` в `Destroy` только по одному из нескольких контейнеров → потеря данных.
- `UTF8Encode(...)` вокруг пути, передаваемого в `FileExists`/`LoadFromFile`.
- `UTF8Decode` перед передачей в `UnicodeString` (FPC vs Delphi — разное).
- `class abstract(TInterfacedObject)` + ручной `Free` → путаница владения и
  подсчёта ссылок; проверяй, как объект реально передаётся (объект или интерфейс).
- Автогенерируемый пакетный юнит правили руками → правка потеряется.
- Алиас типа в фасаде не совпадает с реальным именем класса в модуле →
  пример из README не собирается.
- Комментарий «сбрасываем каждые N записей» при коде без счётчика.

## Что писать в раздел «не проверено»

- Сборка/линк: нет компилятора, нет Lazarus-пакетов, нет зависимых репозиториев.
- Тесты: нет зависимых пакетов, нет GUI/дисплея, тесты требуют ФС/сеть.
- Рантайм-поведение и производительность: не запускалось.
- Платформа/компилятор, которых нет локально (вторая ветка кода остаётся гипотезой).
