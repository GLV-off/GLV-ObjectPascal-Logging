# Линзы принципов: вопросы, ложные трактовки, коллизии

Справочник к `SKILL.md`. Задача — задавать принципам **вопросы о фактах**,
а не искать в коде «нарушения». Ответ «нет наблюдений» — нормальный результат.

---

## SOLID

### S — Single Responsibility
**Суть:** у модуля одна причина изменения — одна группа потребителей, которую
может задеть правка.

- Вопросы: сколько разных людей/сценариев заставляет менять этот тип?
  Сколько полей живёт «сами по себе», не участвуя в главном методе?
- Ложная трактовка: «один метод / одна строка на функцию». Ответственность —
  это причина изменения, а не размер. Форматирование + запись в файл — две
  причины; два метода записи — одна.
- В Pascal: смотри поля `F*` (fan-in полей внутри класса), `uses` юнита и
  методы, которые трогают разные подсистемы (формат/IO/потоки/время).
- Часто сталкивается с: KISS, High Cohesion (одно и то же), Creator.

### O — Open/Closed
**Суть:** добавлять поведение, не правя существующее.

- Вопросы: чтобы добавить новый вид (логгер, формат, уровень), надо править
  существующий код — или добавить новый тип? Кто уже пользуется текущей
  точкой расширения?
- Ложная трактовка: «всё должно быть расширяемым». Расширяемость всегда
  стоит денег и почти всегда спекулятивна.
- В Pascal: наследники `TLog` = готовая точка расширения; `case` по типу
  в одном месте — нормально, пока ветки растут в одном направлении.
- Сталкивается с: YAGNI (главный конфликт), KISS, Protected Variations.

### L — Liskov Substitution
**Суть:** наследник соблюдает контракт базового типа — включая неявные
обязательства (потокобезопасность, владение, «ничего не бросает»).

- Вопросы: что базовый тип обещает вызывающему? Наследник это обещание
  сохраняет? Что будет, если подставить наследника в существующий тест?
- Ложная трактовка: «наследник не бросает исключение» без указания, кто его
  ловит. Контракт определяется потребителем, а не воображением.
- В Pascal: пустой `Log` у наследника, «тихая» потеря сообщений, разное
  поведение при `nil`, разные форматы строк у однотипных классов.
- Сталкивается с: KISS (проверка контракта дороже, когда наследник один).

### I — Interface Segregation
**Суть:** потребитель не должен зависеть от методов, которые не использует.

- Вопросы: сколько методов у базового типа/интерфейса? Все ли потребители
  используют все? Есть ли «широкий» тип ради одного метода?
- Ложная трактовка: дробить на интерфейсы по одному методу.
- В Pascal: базовый класс с одним абстрактным методом (`TLog.Log`) — ISP уже
  выполнен; обратная проблема (толстая база) встречается редко.
- Сталкивается с: KISS (каждый новый интерфейс — новое имя в API).

### D — Dependency Inversion
**Суть:** политика не зависит от деталей; детали зависят от политики.

- Вопросы: где принимается решение «куда писать»? Можно ли подменить
  реализацию, не правя вызывающий код? Зависит ли тип от конкретного
  класса/глобального состояния?
- Ложная трактовка: «DIP = интерфейс на каждый класс / DI-контейнер».
  Абстрактный класс, колбэк, параметр метода — тоже инверсия.
- В Pascal: `class var` + `initialization`-автомонтирование — прямая
  зависимость от глобального состояния; конструктор с параметром-предком —
  инверсия без единого интерфейса.
- Сталкивается с: KISS, YAGNI, Low Coupling (частично совпадает).

## GRASP

Формат: вопрос-линза → чего не делать. GRASP — про распределение
ответственностей; он почти всегда перекрывается с SOLID, поэтому совпадение
двух принципов не считается двумя подтверждениями.

| Паттерн | Вопрос-линза | Ложная трактовка |
|---|---|---|
| **Information Expert** | Кто уже владеет данными, нужными для решения? | «Эксперт = тот, кто вызывает»: перенос данных к вызывающему ломает инкапсуляцию |
| **Creator** | Кто владеет объектом и его временем жизни? | Создание «где удобно» без владения → двойное освобождение |
| **Low Coupling** | Сколько внешних имён нужно знать, чтобы изменить эту единицу? | Связность меряется по interface-`uses`, а не по числу строк |
| **High Cohesion** | Делает ли тип одну связную работу? | = SRP по смыслу; не два независимых аргумента |
| **Controller** | Есть ли точка входа, изолирующая UI/транспорт от логики? | Контроллер-бог, в котором «всё, что не влезло» |
| **Polymorphism** | Ветвление по типу: переопределение или `case`? | «Полиморфизм всегда лучше `case`» — при 2-3 стабильных ветках нет |
| **Pure Fabrication** | Нужен ли искусственный класс ради низкой связности? | Слой «на всякий случай», не связанный с поведением |
| **Indirection** | Помогает ли посредник развязать две стороны? | Посредник, который только пересылает вызов |
| **Protected Variations** | Что именно защищаем от изменения — и оно уже меняется? | Защита от гипотетического изменения (см. YAGNI) |

## KISS

**Суть:** минимум сущностей и понятий на один сценарий.

- Вопросы: сколько файлов/типов/швов нужно понять, чтобы ответить «куда
  попадает сообщение»? Что можно удалить, не потеряв поведение? Есть ли
  два имени для одной вещи?
- Ложная трактовка: «KISS = писать короткие функции» или «KISS = один файл».
  Простота измеряется в понятиях, которые держит в голове читатель, а не в
  строках.
- В Pascal: количество юнитов в `uses` фасада, глубина наследования,
  количество способов сделать одно и то же (две линейки API).

## YAGNI

**Суть:** не строить для требований, которых нет.

- Вопросы: кто **сегодня** пользуется этим параметром/точкой расширения/
  обобщением? Если никто — какое датированное событие сделает это нужным?
  Сколько стоит поддержка этой ставки (доки, тесты, два компилятора)?
- Ложная трактовка: «YAGNI = не писать абстракций вообще». Уже существующий
  шов с несколькими потребителями — не спекуляция. YAGNI про **новые**
  сущности, а не про удаление работающих.
- В Pascal: `overload` ради симметрии, параметры «на будущее», generic-версии
  без потребителя, флаги режимов, которые никто не включает.

## Карта коллизий

Для каждой пары: в чём конфликт и чем он разрешается **в этом репозитории**
(маленькая библиотека, KISS/YAGNI — фильтр).

| Пара | Конфликт | Разрешение |
|---|---|---|
| SRP ↔ KISS | Дробление уменьшает связность внутри типа, но добавляет типы и переходы | Дробить, когда части меняются по разным причинам **и** у них разные потребители; иначе оставить |
| OCP ↔ YAGNI | Точка расширения — это ставка на будущее изменение | Шов оправдан, если расширение уже происходило ≥2 раза или есть второй потребитель сегодня |
| DIP/Indirection ↔ KISS | Прослойка развязывает, но добавляет сущность в путь каждого вызова | Инверсия через параметр/наследование почти всегда дешевле отдельного интерфейса |
| ISP ↔ Low Coupling | Мелкие интерфейсы уменьшают зависимость, но множат имена | При одном методе в базовом типе ISP уже выполнен; не дробить дальше |
| LSP ↔ YAGNI | Контракт наследника надо формализовать и тестировать | Пока наследников мало — контракт живёт в тесте на базовый тип, а не в документе |
| High Cohesion ↔ SRP | Одно и то же под разными именами | Считать одним аргументом; второй раз не засчитывать |
| Information Expert ↔ Low Coupling | Эксперт тянет данные к себе, увеличивая знание о формате | Решать по тому, что чаще меняется: формат или набор вызывающих |
| Polymorphism ↔ KISS | Иерархия против `case` | `case` на 2-4 стабильные ветки дешевле; иерархия — когда ветки растут независимо |
| Protected Variations ↔ YAGNI | Защита от изменения, которого ещё нет | Защищать только то, что уже менялось, или явно названный риск |
| Pure Fabrication ↔ KISS | Искусственный класс ради связности | Оправдан, если он убирает знание из публичного типа (утилиты IO, кодирование) |

## Масштаб меняет ответ

| Масштаб | Что доминирует |
|---|---|
| 10-50 строк, один сценарий | KISS; принципы не применимы, любая структура — накладные расходы |
| 1-3 тыс. строк, библиотека | KISS/YAGNI как фильтр; SOLID только там, где реально будет второй потребитель |
| 10-100 тыс. строк, продукт | OCP/DIP окупаются; цена навигации перестаёт быть главной |
| 100 тыс. +, много команд | SRP/ISP/границы модулей; без них изменения конфликтуют |

Правило: **сначала назови масштаб**, потом спорь о принципах. Половина
«нарушений SOLID» — это принципы не того масштаба.
