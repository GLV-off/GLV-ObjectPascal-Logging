# Карта документации: кто за что отвечает

Документ в этом репозитории — **заявка**, а не истина. Источник истины:
код (`lib/src`), тесты (`test/src`) и фактическое состояние git. Этот файл
фиксирует, какие утверждения можно проверить машинно, а какие остаются
ручной работой.

## 1. Порядок источников

1. Код и тесты: `lib/src/*.pas`, `test/src/*.pas`, `test/pkg/lz/*.lpi`.
2. Инвентарь: `git ls-files`, `find`, содержимое `.gitignore`.
3. `AGENTS.md` — контракты, карта, сборка, известные дефекты.
4. `README.md` — пользовательское описание и примеры.
5. `doc/**` — планы и пояснения; у них разный горизонт (v1/v2/план скиллов).

При расхождении **код/тест важнее текста**. Расхождение — находка `DOC`
(совместимо с `code-recon`), а не разрешение молча править код.

## 3. Машинные проверки `doc-facts.sh`

Скрипт печатает `DOC|<файл>:<строка>|<тип>|<утверждение>|<факт>` и
возвращает `2`, если дрифты есть. Каждая проверка — одна короткая функция.

| Тип | Утверждение | Факт |
|---|---|---|
| `count` | `AGENTS.md:67`: «39 отслеживаемых файлов» | `git ls-files | wc -l` (число меняется) |
| `ignore` | `AGENTS.md:66`: `out/ backup/ *.ppu *.o *.exe *.log *.lps` под `.gitignore` | в `.gitignore` нет `*.o` |
| `path` | `AGENTS.md`/`README.md`: ссылки на `doc/*` — файл должен существовать | после переноса — `doc/v1/...`; актуальный список — вывод скрипта |
| `unit` | `doc/units.md:11`: `GLV.Log.AsyncFileEngine` | в `lib/src` такого юнита нет |
| `format` | `AGENTS.md:96-98`: три формата строк | реализация в `lib/src` (проверка по литералам) |
| `contract` | `AGENTS.md:99`: `AsStr` иначе `UNKNOWN` | в `GlvLogTypes.pas` ветка закомментирована |
| `test-requires` | `AGENTS.md:61`: `Test.lpi` требует `glv_log_contract` | фактически ещё и `glv_log_def_engine` |
| `env` | `AGENTS.md:53`: FPC в `PATH` нет → только Lazarus | S1 `probe.sh`: два FPC вне `PATH`, сборка возможна |

`format` проверяет только наличие формата в коде, а не в тестах: у
`TConsole` теста нет, и это отдельная находка (`TEST`/`GAP`), а не дрифт
документации.

## 4. Что скрипт намеренно не делает

- Не проверяет `backup/`, `out/`, `*.lps`, `*.ppu`, `*.exe`, `*.log`:
  это артефакты и исторические копии, а не документация.
- Не считает ошибкой будущие модули из `doc/v2/design_builder_ru.md` и
  placeholder'ы из `doc/v2/usage.md`: там явно написано, что реализация
  не начата.
- Не проверяет приблизительные числа (`~1400 строк`) и «8 модулей»:
  это оценка/граница v1, а не точный инвентарь.
- Не проверяет CRLF, кодировку и качество комментариев — для этого нужны
  отдельные правила и глаза.
- Не правит ни код, ни доки: только печатает факты.

## 5. Как поступать с дрифтом

1. Зафиксировать находку: `DOC`, `путь:строка`, цитата, фактическое
   значение/файл.
2. Решить отдельно: **обновить доку** (по умолчанию) или **изменить код**
   (только по явному запросу и с тестом).
3. Если меняется контракт (формат строки, имя юнита, пакет), сначала
   обновляются тесты/пакеты, затем код, затем все доки в том же изменении.
4. После правки снова запустить `doc-facts.sh`; остаток — в бэклог S5,
   а не «зелёный» отчёт.
5. В `doc/` сохранять CRLF; `.pi/skills/**` — LF (правило плана).

## 6. Не дублировать

- `code-recon` — поиск и классификация находок; здесь только сверка текста.
- `design-brainstorm` — варианты дизайна; здесь не выбираем архитектуру.
- `pascal-build-probe` — детект компилятора; здесь вызываем его `probe.sh`.
- `pascal-package-sync` — правка `.lpk`/`.lpi`; здесь только читаем пакеты.
- `test-cross` — запуск тестов; здесь используем тесты как источник фактов.
- `backlog-from-review` — хранение долгов; здесь фиксируем `DOC`-находки.
