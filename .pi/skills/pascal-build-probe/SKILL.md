# Проверка сборки Pascal-проекта

Задача скилла — заменить угадывание «есть ли компилятор» на воспроизводимый
протокол: **детект → сборка → лог → честный результат**. Скилл ничего не
исправляет в коде и пакетах; найденная поломка — это факт для отчёта/бэклога.

## Жёсткие правила

1. **Сначала probe, потом build.** Не собирать «наугад» найденным в `PATH`
   компилятором: на этой машине `PATH` пуст, а `PP` указывает в никуда.
2. **Нет запуска — нет «ok».** Наличие `.pas`, `.lpk`, `out/` или старого `.exe`
   не доказательство сборки. Не запускал компилятор — пиши «не проверено».
3. **Лог — доказательство.** Каждый `RESULT|ok` подтверждается строкой
   `lines compiled`/`Linking` в `out/probe/<target>-<stamp>.log`. Пустой или
   обрезанный лог = `fail`, а не «наверное, собралось».
4. **Не смешивать тулчейны.** Два FPC (3.2.2 i386 и 3.3.1 x64) дают разные
   `.ppu` и `fpc.cfg`. Сборка ведётся одним компилятором, каталоги вывода не
   пересекаются.
5. **Не сорить в дереве.** Артефакты — только в `out/` (в git не входит).
   Прямой FPC требует `-FU` (юниты) и `-FE` (exe); без них мусор падает рядом
   с исходниками.
6. **Не править код и пакеты.** Поломка сборки — отдельная задача с отдельным
   тестом и отдельным решением. Здесь только детект, сборка и отчёт.
7. **Внешняя зависимость — только чтение.** `../pas_TestingWrapper` не
   изменять, не собирать в его каталоги, не «обновлять».

## Шаг 1 — детект тулчейна

```bash
bash .pi/skills/pascal-build-probe/scripts/probe.sh
```

Скрипт ищет компиляторы в порядке приоритета: `PATH` → `$PP` → `$FPCDIR` /
`$LAZARUSDIR` → типовые корни (`C:/dev/tools/{lazarus,fpcdelux}`, `C:/lazarus`,
`/usr`, `/usr/lib/fpc`, `/opt/fpc`). Для каждого кандидата проверяется, что
файл существует и запускается (`-iV`, `-iTP`); мёртвые пути не считаются
компиляторами. Отдельно проверяются `lazbuild`, Delphi (`dcc32/dcc64`) и
`GlvTestCross`.

Формат (стабильный, годится для диффа между сессиями):

```text
TOOL|fpc-i386|ok|C:/dev/tools/lazarus/fpc/3.2.2/bin/i386-win32/fpc.exe|3.2.2
TOOL|fpc-x64|ok|C:/dev/tools/fpcdelux/fpc/bin/x86_64-win64/fpc.exe|3.3.1
ENV|PP|stale|C:/dev/tools/lazarus/fpc/3.2.2/bin/x86_64-win64/ppcx64.exe
ENV|LAZARUSDIR|ok|C:/dev/tools/fpcdelux/lazarus
TOOL|lazbuild|ok|C:/dev/tools/fpcdelux/lazarus/lazbuild.exe|5.99
TOOL|delphi|absent|
WARN|mixed-toolchain|LAZARUSDIR=…|fpc=…
WARN|two-fpc|…|…
DEP|GlvTestCross|ok|../pas_TestingWrapper/Pkg/LZ/glvtestcross.lpk|units=…
SUMMARY|fpc=2|lazbuild=1|delphi=0|tests-dep=1
```

Коды выхода: `0` — FPC + lazbuild + зависимость тестов на месте; `2` —
частично; `3` — нет ни FPC, ни lazbuild. Отсутствие тулчейна — результат, а
не сбой скрипта.

Как читать:

- `TOOL|fpc|absent` — компилятора нет: писать «не проверено» и чего не хватает.
- `ENV|PP|stale` — переменная врёт; не использовать `$PP`, брать путь из `TOOL`.
- `WARN|two-fpc` — рядом две установки; зафиксировать в отчёте, какой
  компилятор использован.
- `WARN|mixed-toolchain` — lazbuild и выбранный FPC из разных установок;
  для `.lpi`/`.lpk` доверять lazbuild, для прямого FPC — явному пути.
- `TOOL|delphi|absent` — Delphi-ветка не проверяется; не выдавать её за рабочую.

Типовые ловушки этой машины (две установки, мёртвый `PP`, пути git-bash,
разные каталоги `BuildMode`) — в `references/build-matrix.md`, раздел 4.

## Шаг 2 — сборка

```bash
bash .pi/skills/pascal-build-probe/scripts/build.sh <target> [<target> ...]
```

Цели: `lib-v2`, `lib-v1-ct`, `tests`, `tests-int`, `demo`, `demo-builder`, `all`.
Без аргументов — список целей и код `64`; неизвестная цель — ошибка, не
молчаливый успех. Переменные: `BUILD_MODE=Debug|Release`,
`FPC=<path>` (переопределить компилятор), `LAZBUILD=<path>`,
`LAZBUILD=off` (принудительный фолбэк на fpc).

Логика: `lazbuild` для `.lpi` (с `--build-mode`) и `.lpk` (без режима);
если `lazbuild` нет — прямой `fpc` с `-Mdelphi`, `-Fu/-Fi` на `lib/src` и
`test/src`, `-Fu` на `../pas_TestingWrapper/Src`, `-FU out/probe/units-*`,
`-FE out/probe/bin-*`. `.ctpkg` через `lazbuild` не собирается — цель
`lib-v1-ct` компилирует фасад `GlvLog.pas`.

Скрипт печатает вывод `probe.sh`, затем по цели:

```text
RESULT|tests|ok|C:/dev/glv/pas_Log/out/probe/tests-20261028-221935.log
RESULT|demo|skipped|нет ни lazbuild, ни fpc
SUMMARY|ok=1|fail=0|skipped=0|logs=out/probe
```

Код выхода: `0` — все цели `ok`; `1` — есть `fail`; `2` — ничего не собрано
(все `skipped`); `64` — ошибка аргументов.

## Шаг 3 — отчёт

Пиши дословно, без пересказа:

1. `TOOL`/`ENV`/`WARN`/`SUMMARY` из probe (или ключевые строки).
2. По каждой цели: `ok`/`fail`/`skipped`, путь к логу, код выхода.
3. Если `fail` — первые 5–10 строк ошибки и вывод «компилятор/пакет/исходник»;
   не диагностировать по одной строке, смотреть весь лог.
4. Что **не** проверено: Delphi, CodeTyphon, запуск тестов (сборка ≠ прогон),
   рантайм — с причиной.

Провал сборки не повод править код в этой сессии: это вход для
`backlog-from-review` (класс `BLOCKER`/`BUG`) с дословным логом.

## Не дублировать

- `code-recon` — read-only ревью и находки; он **не собирает** и не заменяет
  этот протокол. Здесь не ищем дефекты кода, только проверяем сборку.
- `design-brainstorm` — варианты дизайна, не сборка.
- `pascal-package-sync` (`S2`) — покрытие юнитов пакетами, правка `.lpk`;
  здесь пакеты только собираются как есть.
- `test-cross` (`S3`) — как писать тесты и прогонять харнесс; здесь только
  компиляция тест-проектов.
- `doc-sync-ru` (`S4`) — сверка доков с кодом; здесь доки не трогаем.

## Если окружение недоступно

Сообщить явно: «сборка не проверена», перечислить отсутствующие компоненты
(компилятор, lazbuild, `GlvTestCross`, пакет lib), указать, что именно
запускалось (`probe.sh` / `build.sh` и код выхода). Не заменять проверку
рассуждением о том, что «должно собраться».
